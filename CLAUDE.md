# BrandSim UI-система — правила для агента

Эти правила действуют всегда и приоритетнее умолчаний агента.
`AGENTS.md` — копия этого файла.

## 0. Первый запуск

Ты в учебном репозитории. Здесь UI-система продукта BrandSim без самого
продукта: документы, живой UI-кит и проверка. Тот, кто тебя открыл, скорее
всего, хочет одного из двух:

- **понять, как это устроено** — объясняй по `GUIDE.md`, показывай
  на файлах и на странице кита;
- **повторить у себя** — веди по `REPLICATE.md`, шаг за шагом, на его
  продукте.

Если неясно, чего хотят, — спроси.

### Проверь окружение и скажи, чего не хватает

| Что | Зачем | Без него |
|---|---|---|
| Python 3 | поднять кит: `cd kit && python3 -m http.server 8000` → `http://localhost:8000/kit.html` | кит не открыть |
| bash, python3 | гейт: `bash kit/design-gate.sh` | нет машинной проверки |
| плагин **[superpowers](https://github.com/obra/superpowers)** | скилл `brainstorming`: разбор задачи и визуальный компаньон (правило 2) | варианты показывать в чате текстом |
| MCP **refero-styles** | основа стиля для `DESIGN.md` (правило 6) | стиль подбирать самому |

Несущее здесь — первые две строки. Остальное — инструменты, их роль важнее
их самих (см. `GUIDE.md`, «Поддерживающее»). Не требуй всё сразу: назови,
чего нет, и что это значит.

### Карта репозитория

```
PRODUCT.md, DESIGN.md        продукт и дизайн-система
KIT-RULES.md, KIT-BINDING.md ядро описания кита и привязка к стеку
UI-KIT.md                    спека страницы кита
GUIDE.md, REPLICATE.md       как устроено / как повторить
kit/                         живой кит, стили, иконки, шрифты, гейт
```

# Как мы работаем над дизайном

## 1. Не трогаем то, что не интерфейс

В исходном проекте правился только фронт; модель симуляции была чужой
зоной. Если задача по интерфейсу упирается в данные или логику — остановись
и скажи, а не «поправь чуть-чуть». Нужно новое поле в ответе сервера —
сначала озвучь, а не меняй молча. (Здесь модели нет, но правило — часть
системы: у студента граница будет своя.)

## 2. Сначала визуальный компаньон, только потом код

Порядок для любой визуальной задачи — строго такой:

1. Разобрать, что именно правим и зачем.
2. Собрать варианты в визуальном компаньоне плагина [superpowers](https://github.com/obra/superpowers)
   (скилл `brainstorming`: локальная страница в браузере, наружу ничего не
   уходит) — композиция, набор элементов, альтернативы.
3. Показать варианты.
4. **Дождаться явного подтверждения.** Не «кажется, ок», а прямое «да,
   этот вариант».
5. Только после этого — правки в коде.

**Вопросы — всегда в чат.** Ни форм, ни блоков «Open Questions» внутри
компаньона: там они остаются незамеченными. Компаньон — для картинок; выбор
запрашивается сообщением.

**Пока в компаньоне нет утверждённого результата — в файлах интерфейса не
меняется ничего.** Ни «пока подготовлю разметку», ни «сделаю черновик, потом
поправим». Любой промежуточный шаг согласовывается. Молчание — не согласие.

## 3. Продукт и дизайн живут в корне: `PRODUCT.md` и `DESIGN.md`

- `PRODUCT.md` — продуктовая правда: пользователи, назначение,
  ограничения, терминология.
- `DESIGN.md` — дизайн-система: токены, шрифты, цвета, отступы,
  компоненты. Появляется из работы над визуальным миром и дальше служит
  эталоном для гейта приёмки (правило 5).

Отдельной папки для дизайна нет.

## 4. Всегда опираемся на референс: `DESIGN.md` и UI-кит

| Что | Где | Отвечает на вопрос |
|---|---|---|
| дизайн-система | `DESIGN.md`, токены — `:root` в `kit/styles.css` | какие шрифты, цвета, отступы, размеры |
| UI-кит | `kit/kit.html` + `kit/kit-specs.js` (описания), `kit/kit.js`, `kit/kit.css`; живой — `http://localhost:8000/kit.html` | какие компоненты есть, с какими опциями и состояниями |
| правила кита | `KIT-RULES.md` (ядро), `KIT-BINDING.md` (как сделано здесь + аудит долгов) | как описывать компонент |

Если что-то нарушает референс — **идём и правим сразу же**, а не
записываем в «потом». Не копим долг.

### Кит в работе

- **До вариантов.** Прежде чем рисовать варианты в компаньоне (правило 2),
  пройди по каталогу кита: есть ли уже компонент, а у него — опция или
  состояние, которые закрывают задачу. Варианты собираются из существующих
  компонентов. Второе поле, вторая кнопка «почти как первая» — главная
  поломка, от которой кит и защищает (`KIT-RULES.md`, «Зачем»).
- **Новый компонент или новая опция** — отдельный пункт, который называешь
  при показе вариантов: «здесь в ките такого нет, заводим». Тихо не
  заводишь.
- **Вместе с кодом.** Если правка меняет форму компонента, добавляет
  опцию, состояние или новый компонент — описание в `kit/kit-specs.js`
  правится в той же правке, по `KIT-RULES.md`. Новые токены — в
  `DESIGN.md` и в таблицы кита там же.
- **Долги из аудита** (`KIT-BINDING.md` → «Аудит текущего кита») —
  расхождения продукта, решение по которым за владельцем продукта.
  Попутно не чинишь; если задача их задевает — говоришь. Новое
  расхождение, найденное по ходу, — строкой в ту же таблицу.
- Схемы в ките — без описаний и пояснений: карточка = заголовок, матрица,
  стенд.

## 5. Гейт приёмки: проверка по дизайн-системе

Перед тем как сказать «часть работы сделана» — **всегда** пробегись по
изменённому и убедись:

- используются **только** переменные и варианты из дизайн-системы;
- нет захардкоженных значений: magic numbers в отступах, hex-цвета мимо
  токенов, шрифты и размеры вне шкалы;
- ничего не нарушает референс;
- компонент, который поменялся или появился, описан в ките, и его карточка
  на `kit.html` рисуется во всех состояниях матрицы.

Машинная часть — скрипт гейта:

```bash
bash kit/design-gate.sh
```

Проверки: hex мимо токенов, синий, следы тёмной темы, id брендов в
интерфейсе, контрольные ширины, иконки мимо `icons.js`, двойники состояний
и описания кита по контракту (`kit/kit-contract-check.py`). Ненулевой код —
работа не сдана. Скрипт видит не всё: что он не проверяет, перечислено в
`KIT-BINDING.md`, п. 10, — это смотришь глазами.

Нашёл нарушение → чинишь до конца, и только потом отчитываешься. Отчёт
«готово, но там пара хардкодов осталась» недопустим. Проверка обязательна
каждый раз, а не по запросу.

## 6. Refero — основа стиля

MCP-сервер `refero-styles` (community-сервер
`faridjafarlee/refero-styles-mcp-server` поверх `styles.refero.design`,
ключ не нужен) — **только стили**: типографика, цвет, настроение, готовые
`design.md`.

| Инструмент | Что делает |
|---|---|
| `refero_match_style` | **основной** — подбирает стиль по описанию проекта |
| `refero_search_styles` | поиск по ключевому слову, настроению, бренду, цвету |
| `refero_list_styles` | листать каталог целиком |
| `refero_get_design_md` | полный `design.md` конкретного стиля |

Берём отсюда **основу дизайн-системы**: шрифтовые шкалы, цветовые системы,
общее настроение. `design.md` от Refero — стартовый материал для нашего
`DESIGN.md`, а не готовый ответ. Тянем его до вариантов в компаньоне, итог
фиксируем в `DESIGN.md`; гейт проверяет по нашему файлу, а не ходит в MCP.
