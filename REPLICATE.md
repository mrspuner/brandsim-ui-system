# Повторить у себя — инструкция для агента

Этот файл для тебя, агент. Студент хочет такую же систему для своего
продукта. **Ты проходишь шаги сам и приносишь первую версию каждого
файла.** Студент не пишет с нуля: он читает, поправляет и говорит «да».

Перед стартом прочитай `GUIDE.md`: из него ясно, что в шагах несущее, а
что можно упростить.

## Как работать

- **Сначала собери материал, потом спрашивай.** Код продукта, экраны,
  скриншоты, тексты, сайт — всё, что студент может дать. Вопросы задавай
  только про то, чего в материале нет. По одному вопросу за сообщение.
- **Каждый шаг заканчивается черновиком,** а не вопросом «как сделать».
  Где пришлось угадывать, пометь в файле: `<!-- догадка: … -->`.
- **Нет «да» — нет следующего шага.** Покажи результат шага, коротко
  перечисли догадки, дождись подтверждения. Молчание не считается
  согласием.
- **Наши файлы — образец формы, а не текст для подстановки.** Структура
  и уровень детальности берутся отсюда, содержание — из продукта студента.
  Слов BrandSim, холодильники, бренды, рычаги в его файлах быть не должно.
- Если продукта ещё нет в коде (только идея или макеты), шаги 4–6 делай
  по макетам, а кит собирай как отдельную страницу.

## Шаг 0. Что есть

Спроси, где лежит продукт и что о нём можно прочитать. Пройди по
материалу и одним сообщением назови: стек, экраны, есть ли уже токены или
дизайн-система, какие инструменты из `CLAUDE.md` § 0 у студента есть.

**Выход:** короткая сводка «что нашёл / чего не хватает».

## Шаг 1. `PRODUCT.md`

Заполни разделы нашего `PRODUCT.md` по материалу: пользователи,
назначение, контекст использования, ограничения, терминология. Термины
вытащи из интерфейса и текстов продукта, а не придумывай.

**Готово, когда** по файлу понятно, кто пользователь, в какой ситуации он
работает и как называются главные вещи. Студент подтвердил.

## Шаг 2. `DESIGN.md` и токены

Если стиль у продукта уже есть, вытащи его из CSS: какие значения реально
используются и какие повторяются. Если стиля нет, подбери основу через
Refero (`refero_match_style` по `PRODUCT.md`) и предложи 2–3 направления
на выбор. Заведи токены в CSS (`:root`) и в таблицы `DESIGN.md`
одновременно, по образцу нашей трёхъярусной схемы из `UI-KIT.md`,
«Архитектура токенов».

**Готово, когда** у каждого цвета, размера шрифта и отступа есть имя и
студент выбрал направление. Значения мимо токенов, найденные в коде,
выпиши списком.

## Шаг 3. Ядро и привязка

Скопируй `KIT-RULES.md` без изменений. Возьми форму из начала
`KIT-BINDING.md` (десять вопросов) и ответь на неё для стека студента.
На что ответа пока нет, оставь пустым с пометкой.

**Готово, когда** заполнены пункты 1–3 и 7, остальные помечены.

## Шаг 4. Инвентарь

Пройди по экранам и выпиши все элементы интерфейса. Найди «почти
одинаковые»: кнопки, которые отличаются одним отступом, три оттенка
серого, поля с разной высотой. Для каждой группы двойников предложи, какой
вариант оставить.

**Выход:** список компонентов по слоям (атом / молекула) и таблица
двойников с твоим предложением. Решение по двойникам принимает студент.

## Шаг 5. Первые компоненты и страница кита

Опиши 3–5 самых частых атомов по `KIT-RULES.md`: опции, состояния,
контент. Подними страницу кита: формат описаний и `force` возьми из
нашего `kit/kit-specs.js` и `kit/kit.js`, переложив на стек студента.

**Готово, когда** каждая карточка рисуется во всех состояниях матрицы и
в консоли нет ошибок. Покажи страницу студенту.

## Шаг 6. Гейт

Возьми `kit/design-gate.sh`. Оставь проверки, которые имеют смысл в
продукте студента (hex мимо токенов, иконки, двойники, контракт описаний).
Проверки, завязанные на наш продукт, перепиши или убери. Каждую проверку
проверь дважды: на чистом коде она зелёная, на нарочно внесённом
нарушении красная.

**Готово, когда** гейт проходит на коде студента, а на внесённом hex
падает.

## Шаг 7. `CLAUDE.md` студента

Перенеси правила 2–5 нашего `CLAUDE.md` (варианты → «да» → код; где живут
файлы; референс и кит; гейт) с путями студента. Правило 6 добавь, только
если Refero у него есть.

**Готово, когда** в новой сессии агент по этому файлу сам предлагает
варианты до кода и прогоняет гейт перед отчётом.

## После

Скажи студенту, как дальше держать систему живой: правка формы компонента
идёт вместе с правкой его описания в ките, а найденное расхождение либо
сразу чинится, либо записывается строкой в аудит `KIT-BINDING.md`.
